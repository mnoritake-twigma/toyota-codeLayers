# Codex への依頼プロンプト

> 使い方：`AGENTS.md` をリポジトリのルートに置いてコミットしてから、下の「プロンプト本文」を
> Codex にそのまま貼る。Codex はルートの AGENTS.md を自動で読むので、背景とルールは
> そちらに集約してある。プロンプトでは作業範囲・順番・完了条件だけを渡す。

---

## プロンプト本文

```
このリポジトリ（twigma-ces/toyota-codeLayers）に、Figma Code layers のEnablementセッションで使う
デモ用の試乗申し込みアプリを作ってください。

まずルートの AGENTS.md を全部読んでください。背景・セッションの流れ・技術スタック・
Figma でクローンするための要件・やらないことが書いてあります。AGENTS.md と
このプロンプトが食い違ったら AGENTS.md を優先し、食い違いを最後に報告してください。

## 作るもの

参考サイト（lexus.jp の試乗予約）と同じ5ステップの「申し込み」フローを、架空ブランド
「LUMIÈRE」で再現します。画面のロゴ位置はテキストの「LUMIÈRE」で、ロゴ画像は作らないでください。
これは「見直し前の現行フロー」なので、改善案は入れないでください。改善はセッション中に
Figma 側で作ります。現行フローの不便さ（県で検索すると店舗が多い、試乗車登録のない店舗が
混ざって電話案内で止まる、日時の都合が分からないまま店舗を選ぶ）はそのまま残してください。

## 進め方（この順で、各フェーズの終わりにコミット）

Phase 1: 土台
- Vite + React + TypeScript + Tailwind + react-router-dom。Node 20。
- スタイルは AGENTS.md §9 の LUMIÈRE DS（src/ds/）経由。DS の作成は別プロンプト
  （CODEX_PROMPT_DS.md）で行う。コンポーネント内で色コードや px を直書きしない。
- src/config.ts / src/config.public.ts（AGENTS.md §5 のとおり）。
- npm run dev / npm run build / npm run lint / npm run typecheck が通ること。

Phase 2: Supabase
- supabase/migrations にテーブル定義と RLS（AGENTS.md §4）。
- supabase/seed.sql にモデル10・都道府県47・店舗約150・車両登録（dealer_vehicles）。
  車両は1台ずつ { dealer_id, model_code, kind: 'test_drive' | 'display', grade, body_color,
  interior_color }。1店舗に0〜3台。東京都で検索すると30件前後、そのうち選んだモデルの
  車両登録がない店舗が1〜2割、登録はあるが展示車だけ（試乗できない）の店舗が1〜2割になる配分にする。
  同じ内容を src/data/seed/*.json にも出力するスクリプト（scripts/export-seed.ts）を用意。
- supabase/functions/search-dealers：入力は { modelCode, prefectureCode } または
  { modelCode, postalCode }。返すのは店舗一覧と、各店舗に登録された選んだモデルの車両
  （試乗車・展示車、グレード、ボディカラー、インテリアカラー）。郵便番号のときは
  郵便番号先頭3桁の代表座標からの距離を distanceKm として付け、距離順。都道府県のときは
  店舗コード順（現行の不便さとして、試乗車の有無で並び替えない）。?delay=ms 対応。CORS 対応。
- supabase/functions/submit-request：入力を検証して test_drive_requests に保存し、
  受付番号を返す。希望日時は第1希望・第2希望の「希望」として保存（確定ではない）。
- 空き枠・仮押さえの API は作らない。

Phase 3: 画面（現行フロー）
- 1 モデルを選択：10車種のカード（画像は AGENTS.md §8 の条件を満たす AI 生成画像、なければプレースホルダ）。
- 2 販売店を選択（参考サイトの挙動をそのまま再現する）：
  - 上に「ご希望のモデル」行（選んだモデル＋「変更する →」）。
  - 「都道府県から検索」「郵便番号から検索」のタブ → 検索 → 結果をグレーの帯の中に出す。
  - 店舗はアコーディオン。閉じた状態では店舗名・サムネイル枠・住所・定休日・営業時間しか
    見えず、**試乗車があるか、どのグレード・色かは「＋」で開くまで分からない**（現行の不便さ）。
  - 開くと車両テーブル（モデル／ボディカラー／インテリアカラー）。行の先頭に Tag
    「試乗車」（bright）または「展示車」（weak）。**選べるのは試乗車の行だけ**で、行を押すと
    その1台が選ばれて次へ進む。展示車の行は選べない。
  - 選んだモデルの車両登録がない店舗は、一覧の後ろに見出し「電話で問い合わせする」と
    「下記のお近くの店舗について、試乗車、展示車の登録がございませんが、事前にご連絡いただければ、
    試乗車、展示車をご用意できる場合がございます。お気軽にお近くの店舗までお問い合わせください。」
    を置き、店舗名と電話番号を並べる。
- 3 情報の入力：氏名・フリガナ・メール・電話・第1希望日時・第2希望日時・備考。
  希望日時は独立コンポーネント（PreferredDateTimeField）にする。
- 4 入力内容の確認 → 5 お申し込み完了（受付番号と「販売店より確認のご連絡を差し上げます」）。
- 上部に StepIndicator（進行状況 n/5）。
- 状態：読み込み中・0件・API エラー・オフラインデータ表示中、をそれぞれ画面で表現する。
- コンポーネントは AGENTS.md §6 の構成に従う。DealerCard（閉じた状態の店舗項目）と
  VehicleTable（開いた中の車両テーブル）は単体で props だけで描画できるようにする
  （Figma で磨いて差し替えやすくするため）。
- 店舗の並び替えとフィルタは src/features/dealers/sortDealers.ts の純関数に置く。
- src/api/ の冒頭コメントに「このシステムで取れるのは店舗一覧と、店舗に登録された車両
  （試乗車・展示車、グレード、色）まで。
  空き枠・仮押さえは販売店システム側にあり、API は存在しない」と書く。

Phase 4: 仕上げ
- README.md に：目的（デモ用・本番ではない）、ローカル起動、Supabase の作成手順
  （supabase CLI で link → db push → seed → functions deploy のコマンド）、
  config.public.ts に入れる値、Figma Code layers でクローンする際の確認事項
  （公開到達・プライベート npm 不使用・Fullシート・管理者のクローン許可）。
- sortDealers と api/ のフォールバックに最小限のテスト（Vitest）。
- 最後に、AGENTS.md §3 のステップ2の案A（近い順＋試乗車ありを先頭）と
  案B（日時を先に聞く）が、それぞれどのファイルを触れば作れるかを README の
  「セッションで変更される想定の箇所」に書く。実装はしない。

## 制約
- UIライブラリは入れない。依存は最小限（public npm のみ）。
- 実在ブランド名・ロゴ・写真は使わない。車種名・店舗名・住所は架空。
  画像は AGENTS.md §8 の条件を満たす AI 生成画像のみ。
- 日本語UI、敬体。文言は実サイトのトーンに合わせる。
- service_role key をどこにも書かない。

## 完了報告に含めること

- npm run build / test の結果
- 私が手でやる必要がある作業（Supabase プロジェクト作成、キーの設定、関数デプロイ）
- AGENTS.md との食い違いや、判断に迷って仮置きしたこと
```

## 補足（Codex に渡す前に自分で決めておくこと）

- **Figma 側の事前確認**（コードができた後）：GitHub 組織での Figma GitHub app 承認、
  リポジトリの「Allow cloning to Figma cloud」、クローン後に Supabase へ到達できるか、
  到達できない場合にオフラインデータ表示へ切り替わるか。
